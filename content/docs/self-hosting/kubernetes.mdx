From v0.11, Open Chat Interface has a Helm chart, released with the application: chart `0.11.0` deploys images `v0.11.0`. It is published to GHCR as an OCI artifact, `oci://ghcr.io/ncecere/charts/open-chat-interface`, and lives in the repository at `deploy/helm/open-chat-interface`.

<Callout title="PostgreSQL, Redis and S3 are yours">
  The chart bundles no database and no Redis. Run them with an operator (CloudNativePG, Crunchy, Zalando/Patroni; a Redis operator with Sentinel) or use managed services. For a layout with several replicas of everything, see [High-availability deployment](/docs/self-hosting/high-availability).
</Callout>

## What it runs

| Resource | Purpose |
|---|---|
| Deployment `<release>-api` | The API, as `OCI_ROLE=web` when the worker is enabled (otherwise `all`). Rolling update with `maxUnavailable: 0`, a `preStop` sleep, and a drain on `SIGTERM`. |
| Deployment `<release>-worker` | Background jobs (`OCI_ROLE=worker`): imports, embeddings, summaries, webhooks, backups, compliance exports, retention and background migrations. Serves only health and `/metrics`. |
| Deployment `<release>-web` | Caddy from the web image: the app, and the same-origin `/api` proxy that decides the client address. |
| Service `<release>-web` | Everything, the app and `/api`, goes here. Point your Ingress or HTTPRoute at it. |
| Services `<release>-api`, `<release>-api-headless` | The headless one is how Caddy finds API pods: it balances across them itself and takes a draining pod out of rotation. |
| Jobs `<release>-migrate`, `<release>-migrate-post` | Helm hooks: `migrate` before the rollout, `migrate --post` after it. |
| PodDisruptionBudgets, NetworkPolicies | One pod of each kind down at a time; the API reachable only from the web pods and metrics scrapers. |
| Optional | HorizontalPodAutoscalers, Ingress, Gateway API HTTPRoute, ServiceMonitor, PrometheusRule, a PersistentVolumeClaim for local attachments. |

`<release>` stands for the release name followed by `-open-chat-interface`, such as `oci-open-chat-interface-api`.

## Install

<Steps>
<Step>

### Create the runtime Secret

Every key of the Secret becomes an environment variable of the API, worker and migration pods. `DATABASE_URL`, `AUTH_SECRET` and `ENCRYPTION_KEY` are required; `REDIS_URL` is required for more than one replica (the chart's default). Create it from your secret manager (External Secrets, Sealed Secrets, Vault), never from values. By hand:

```sh
kubectl create namespace oci
kubectl -n oci create secret generic oci-runtime \
  --from-literal=DATABASE_URL='postgres://oci:...@postgres-rw.db:5432/oci' \
  --from-literal=REDIS_URL='redis://:...@redis.cache:6379' \
  --from-literal=AUTH_SECRET="$(openssl rand -base64 48)" \
  --from-literal=ENCRYPTION_KEY="$(openssl rand -base64 48)" \
  --from-literal=METRICS_TOKEN="$(openssl rand -hex 24)" \
  --from-literal=INITIAL_ADMIN_EMAIL=morgan.lee@example.edu
```

`CONTROL_DATABASE_URL`, `READ_DATABASE_URL`, Redis passwords, SMTP or S3 values go in the same Secret, or another one added with `extraEnvFrom`.

</Step>
<Step>

### Install the chart

```sh
helm install oci oci://ghcr.io/ncecere/charts/open-chat-interface --version 0.11.0 -n oci \
  --set secrets.existingSecret=oci-runtime \
  --set config.appUrl=https://chat.example.edu \
  --set web.trustedProxies='10.244.0.0/16' \
  --set ingress.enabled=true --set ingress.className=nginx \
  --set 'ingress.hosts[0].host=chat.example.edu'
```

`helm show values oci://ghcr.io/ncecere/charts/open-chat-interface --version 0.11.0` prints every value with its comment. From a checkout of the repository, use the path `deploy/helm/open-chat-interface` instead. The images are public, so no pull secret is needed.

With `INITIAL_ADMIN_PASSWORD` unset, a one-time password for the first administrator is printed to the API log on the first start: `kubectl -n oci logs deploy/oci-open-chat-interface-api`.

</Step>
<Step>

### Configure attachment storage

Before people upload files, configure S3-compatible storage under **Admin → Data & storage → Storage**. Several API and worker pods read and write attachments, and without S3 (or `storage.persistence` with a `ReadWriteMany` claim) local files live in an emptyDir and are lost when a pod is replaced.

</Step>
<Step>

### Set it up

Sign in as the first administrator and follow the setup checklist: [First run](/docs/administration/first-run).

</Step>
</Steps>

## Values that matter

Every key is documented in the chart's `values.yaml` and checked by its schema; unknown keys are refused.

| Key | Default | Notes |
|---|---|---|
| `secrets.existingSecret` | `""` | The runtime Secret above. `secrets.values` renders one from values, for evaluation only (it is stored in the Helm release). |
| `config.appUrl` | `""` (required) | The address people use; must match the ingress host and scheme. |
| `config.authTrustedOrigins` | `""` | `AUTH_TRUSTED_ORIGINS`: identity providers on private networks. |
| `config.shutdownDrainTimeoutMs` | `25000` | How long a stopping pod lets replies finish. |
| `config.migrationLockTimeoutMs`, `config.migrationStatementTimeoutMs`, `config.postMigrationStatementTimeoutMs` | `""` | Empty uses the defaults (3 s, 15 minutes, four hours). |
| `config.env` | `{}` | Any other plain variable, such as `DISPLAY_TIMEZONE` or `REDIS_SENTINEL_NAME`. |
| `redis.sentinels`, `redis.clusterNodes` | `""` | Become `REDIS_SENTINELS` and `REDIS_CLUSTER_NODES`. Passwords go in the Secret. |
| `image.api.tag`, `image.web.tag` | the chart's `appVersion` | Keep both on the same release. `image.{api,web}.digest` pins a `sha256:` digest. |
| `api.replicaCount`, `web.replicaCount` | `2`, `2` | |
| `worker.enabled`, `worker.replicaCount` | `true`, `1` | Two workers for availability during node drains; one is enough for throughput. With the worker off, the API runs the jobs (`OCI_ROLE=all`). |
| `web.trustedProxies` | `""` | Your ingress controller's pod range, space-separated. Empty: everybody appears to come from the ingress controller. |
| `api.autoscaling`, `web.autoscaling` | off | CPU at 70 % by default; add custom metrics under `metrics`. |
| `storage.persistence.enabled` | `false` | A PVC for local attachments; `ReadWriteMany` with several pods. |
| `ingress.*`, `httpRoute.*` | off | Both route to the web Service. |
| `networkPolicy.enabled` | `true` | See [Client addresses and the network policy](#client-addresses-and-the-network-policy). |
| `metrics.serviceMonitor.enabled`, `metrics.prometheusRule.enabled` | `false`, `false` | See [Monitoring](#monitoring). |
| `migrations.enabled` | `true` | The migration hooks. `false` lets a single API replica migrate itself at startup. |

For streaming, the ingress must not buffer responses and must allow long reads. With ingress-nginx, for example:

```yaml
ingress:
  enabled: true
  className: nginx
  annotations:
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
    nginx.ingress.kubernetes.io/proxy-body-size: 512m
```

## Upgrading with Helm

```sh
# 1. Preflight, changing nothing: the target image against the database.
kubectl -n oci run oci-upgrade-check --rm -i --restart=Never \
  --image=ghcr.io/ncecere/open-chat-interface/api:vX.Y.Z \
  --overrides='{"spec":{"containers":[{"name":"oci-upgrade-check","image":"ghcr.io/ncecere/open-chat-interface/api:vX.Y.Z","command":["node","dist/scripts/upgrade-check.js"],"envFrom":[{"secretRef":{"name":"oci-runtime"}}]}]}}'

# 2. Upgrade: migrate, rolling update, migrate --post.
helm upgrade oci oci://ghcr.io/ncecere/charts/open-chat-interface --version X.Y.Z \
  -n oci --reuse-values --timeout 30m
```

`helm upgrade` is the [three-phase upgrade](/docs/self-hosting/upgrades):

1. **Pre-upgrade hook**, `node dist/migrate.js`: the pre-deploy migrations, with the previous release still serving. If it fails, no pod is replaced.
2. **Rolling update** of the API, worker and web Deployments, one pod at a time, each API pod draining as it stops. Pods run with `RUN_MIGRATIONS=false` and `RUN_POST_MIGRATIONS=false`.
3. **Post-upgrade hook**, `node dist/migrate.js --post`. Its init container first waits until the API and worker rollouts have finished and no pod of the previous release is still terminating, so post-deploy steps never run beside the previous release, even without `--wait`. It reads the Deployments and lists Pods with a token and a Role that exist only for the hook.

Helm waits for hooks for at most `--timeout` (five minutes by default): give it the preflight's estimate for index builds. The hook Jobs are kept until the next upgrade, for their logs (`kubectl -n oci logs job/oci-open-chat-interface-migrate-post --all-containers`). A failed post-upgrade hook leaves the new release running without its new indexes; fix the cause and run `helm upgrade` again, which resumes. Background migrations then run on the worker.

## How draining is wired

The chart applies [draining](/docs/self-hosting/upgrades#replacing-replicas-draining) to Kubernetes:

- a `preStop` sleep (`api.preStopSleepSeconds`, 5 s) so Service endpoints, kube-proxy and Caddy's 2-second DNS refresh stop sending new requests before the drain starts (`api.preStopSleepAction: true` uses the native `sleep` action on Kubernetes 1.30 and later);
- readiness on `/api/health/ready` every 2 s with one failure, liveness on `/api/health/live` (which stays `200` while draining), and a startup probe;
- `terminationGracePeriodSeconds: 40` against the 25-second drain; the chart refuses values where the grace period does not exceed drain plus `preStop`;
- `maxUnavailable: 0` (required) and PodDisruptionBudgets, so a replacement is ready before a pod drains and a node drain stops one pod of each kind at a time.

The web pods find API pods through the headless Service, which lists only ready pods, and Caddy balances across them itself, so its passive checks take one draining pod out of rotation. Workers get the same grace period and no `preStop`: nothing routes to them.

## Client addresses and the network policy

OCI records a client address on sessions and in the audit log, and limits failed sign-ins per address. Caddy in the web pods decides it: it trusts `X-Forwarded-For` only from `web.trustedProxies`, and passes the API exactly one address. So:

- route **all** traffic, `/api` included, to the web Service; never expose the API Service through an Ingress;
- keep `networkPolicy.enabled` (the default): the API accepts connections only from the web pods and from metrics scrapers (`networkPolicy.metricsFrom`, the `monitoring` namespace by default), so nothing else in the cluster can set the header; workers accept only scrapers;
- restrict who reaches the web pods with `networkPolicy.webFrom`, such as your ingress controller's namespace;
- a `LoadBalancer` web Service sees the node's address unless `externalTrafficPolicy: Local` (or the PROXY protocol) keeps the client's.

Egress rules are off by default, since the database, Redis, S3, model providers, connectors and webhooks are different everywhere. `networkPolicy.egress.enabled` with `networkPolicy.egress.extraEgress` restricts them.

## Security

Every pod runs as non-root with a read-only root filesystem, the `RuntimeDefault` seccomp profile, no privilege escalation and every capability dropped, and passes the Pod Security `restricted` profile. Only `/tmp`, the attachment directory and Caddy's `/data` and `/config` are writable (emptyDir or the storage volume). No pod mounts a service account token, apart from the post-upgrade hook's init container.

To run a web image older than v0.11 with this chart, set `containerSecurityContext.web.capabilities.add: [NET_BIND_SERVICE]`: those images carry a file capability that fails to execute with every capability dropped.

## Monitoring

`/metrics` is served on every API and worker pod when `METRICS_TOKEN` is in the Secret. With the Prometheus Operator:

```yaml
metrics:
  serviceMonitor:
    enabled: true          # reads METRICS_TOKEN from the Secret
  prometheusRule:
    enabled: true          # the service objectives' rules and alerts
    labels:
      release: kube-prometheus-stack   # whatever your Prometheus selects rules by
```

The `PrometheusRule` holds the same rules as `deploy/monitoring/prometheus-rules.yaml`. Enable it in one release per Prometheus. See [Service objectives and alerts](/docs/self-hosting/health-and-monitoring#service-objectives-and-alerts).

## Autoscaling

`api.autoscaling.enabled` scales on CPU. To scale on OCI's own metrics, expose them through a custom metrics adapter (prometheus-adapter, KEDA) and add the metric under `api.autoscaling.metrics`; the chart's README has a per-pod request rate example. Replies are long-lived streams, so scale down slowly (`api.autoscaling.behavior.scaleDown.stabilizationWindowSeconds: 600`); each pod removed drains like any other. Workers scale by `worker.replicaCount`.

## How the chart is tested

CI lints and renders the chart with Helm 3 and 4, validates the manifests, and on `linux/amd64` and `linux/arm64` installs it on kind in a namespace that enforces `restricted`: readiness through the web Service, `helm test`, the network policy, then `helm upgrade` to a new tag under load, which must fail no request.

## Without the chart

The images run on Kubernetes without changes if you build your own manifests. Follow what the chart does:

- a pre-upgrade Job running `node dist/migrate.js`, the API Deployment with `RUN_MIGRATIONS=false`, and, after `kubectl rollout status` reports the rollout finished and no old pod is still terminating, a Job running `node dist/migrate.js --post` (no `activeDeadlineSeconds` shorter than its index builds, and `backoffLimit` above zero);
- the probes, `preStop` sleep and grace period above;
- a headless Service for the API, with the web pods' `API_UPSTREAM_HOST` and `API_UPSTREAM_PORT` pointing at it;
- a separate worker Deployment with `OCI_ROLE=worker` and the API on `OCI_ROLE=web`, or the API alone on `all`;
- a NetworkPolicy that admits only the web pods to the API.
