## General

**Appearance & features → General** (`/admin/settings/general`).

<Screenshot slot="admin-general-settings" />

| Setting | Default | What it does |
|---|---|---|
| **Default system prompt** | Built-in | Sent with every conversation; a person's customization is added after it. Keep it short: it is charged on every message, and it is the first thing to suspect when replies drift. |
| **Default reasoning level** | Instant | Where the effort control starts in a new conversation: Instant, Low, Medium or High, lowered to Instant when the model or the person's role does not allow it. |
| **Tool step limit** | 8 | How many steps one reply may spend using [tools](/docs/administration/roles-and-access#tools), 1 to 20. A reply that reaches it gets one more step without tools, so it still answers, and a note says so. |
| **Summarise long conversations** | On | Once a conversation fills about three quarters of its model's input, earlier messages are summarised in the background by that model and the summary is sent instead. Each summary is usage for the person, and is skipped while their allowance is spent. Off, the oldest turns are left out instead; people can still summarise by hand. Messages are never changed either way. |
| **Editorial diagrams** | On | When a role allows artifacts, models are asked to draw diagrams as SVG artifacts in the [Diagram Design](https://github.com/cathrynlavery/diagram-design) style (MIT, Cathryn Lavery), in your [colour theme's accent](/docs/administration/branding#what-follows-branding). Off, only the general artifact guidance remains. |
| **Features** | On, except user memory | Turn off share links, temporary chats, branching, file attachments and user memory for the whole instance. A role can narrow them further on [Roles & access](/docs/administration/roles-and-access#features-and-reasoning-levels). |

Turning a feature off removes it from the interface rather than leaving a control that fails. Web search has its own switch on the [Web search](/docs/administration/web-search) page; the default model is chosen on [Providers & Models](/docs/administration/providers-and-models#the-default-model). User memory is described on [Memory](/docs/administration/memory).

## Email delivery

**Sign-in & security → Email delivery** (`/admin/settings/email`): host, port, TLS, credentials and the address mail is sent from.


Without it, OCI cannot send invitations, password resets, verification or [scheduled reports](/docs/administration/audit-and-reports#scheduled-reports); everything else works. The page calls SMTP configured once a host, port and from address are saved. That is not a delivery test: confirm mail arrives before relying on it. The username and password are write-only.

Requiring email verification does not switch itself off when SMTP is missing or failing; new accounts stay unverified until mail arrives. The Authentication page warns about this, and the setup checklist then marks email as required.

## Storage

**Data & storage → Storage** (`/admin/storage`), with three tabs: the storage driver, the S3 connection, and the upload policy (accepted file types, size and number per message).

<Screenshot slot="admin-storage" />

- **Local** stores files under `STORAGE_LOCAL_PATH` inside the API container. The path is shown but not editable here, so you know which volume to back up. Suitable for one API replica only.
- **S3-compatible** storage is needed for more than one replica. **Test put/read/delete** checks the saved S3 settings work, and can be run while local storage is still active. Run it before switching and after any change. Invalid S3 settings never fall back to local storage silently.

Uploads reserve their allowance before the object is written; deleting a file releases it at once, and the object is removed later by a background job.

## System health

**Data & storage → System health** (`/admin/health`). Whether what OCI depends on is working, [read-only maintenance mode](/docs/administration/maintenance), the replicas running, the background jobs, upgrades and background migrations, storage in use and storage reconciliation. Open this first when something is reported. The checks refresh every 30 seconds while it is open.

<Screenshot slot="admin-health" />

| Check | Warns when | Fails when |
|---|---|---|
| Database | Slow to respond | Not reachable |
| Redis | Not configured, with one replica | Configured but unreachable; or not configured while several replicas share the database |
| Model providers | | None enabled |
| Models | | None enabled |
| Background jobs | Failures in the last day | One started over an hour ago and never finished |
| Email delivery | Not configured | |
| Attachment storage | Uploads never attached to a message | |
| Connectors | An enabled connector's latest exchange failed | |
| Backups | On, but nothing completed in over a day, or objects missing | The latest backup failed |
| Webhooks | An endpoint's latest delivery failed, or deliveries over 15 minutes overdue | |
| Background workers | | No replica that runs background jobs (`OCI_ROLE=worker` or `all`) has checked in for a minute |
| Provider capacity | Messages are waiting for a provider now, waited in the last hour, or a provider answered with rate-limit or overload errors in the last hour | |
| Read-only mode | [Read-only mode](/docs/administration/maintenance) is on: by whom (an administrator, a window or `OCI_READ_ONLY`), until when and why | |
| Cache invalidation | Redis is configured, but the replica answering does not hear other replicas' changes, so they reach it within 30 seconds instead of at once | |
| Encryption keys | | A stored secret needs a key that is neither `ENCRYPTION_KEY` nor in `ENCRYPTION_KEYS_PREVIOUS` |

It also shows *Meaning-based search*, *Compliance export* (with how many people are on legal hold) and *Observability* (whether metrics and traces are on). The summary takes the worst result, so a green banner above a failing row cannot happen.

**Without Redis, one replica is a warning and several are an error.** Replies still work, but reconnecting to a reply in progress is unavailable, and rate limits and provider capacity are counted by each replica on its own, so with several replicas every limit is multiplied by their number. From v0.11 Redis is required for more than one replica.

**Encryption keys** names the current key's id, counts the stored secrets, and says how many still need a previous key (*Previous keys still in use: N values*). After a [key rotation](/docs/self-hosting/security#rotating-encryption_key), keep `ENCRYPTION_KEYS_PREVIOUS` until that reaches 0. Right after an upgrade to v0.11 it says re-encryption waits for `migrate --post`.

### Maintenance

Read-only mode: switch it on, or schedule a window with an announcement ahead of it, and choose which background jobs keep running meanwhile. See [Maintenance](/docs/administration/maintenance).

### Replicas

The API replicas heard from in the last minute, and whether each serves requests, runs background jobs, or both (**Web (API only)**, **Worker (background jobs)**, **API and background jobs**). Shown when Redis is configured. See [Process roles](/docs/self-hosting/high-availability#process-roles).

### Background jobs

The latest run of each scheduled job: when it started, how long it took, how many items it processed, and any error. **Run** starts one now, which is useful after changing a setting it depends on, such as retention. Each job holds a PostgreSQL lock while it runs, so replicas never run the same job at once. If the replica answering only serves requests (`OCI_ROLE=web`), **Run**, **Back up now** and **Export now** are handed to a worker, and refused while no worker is running.

### Upgrades

What upgrading this database involves, for the running release: the database schema, pending pre-deploy migrations and post-deploy steps with the indexes they build, unfinished work a later release needs, and any invalid indexes left by an interrupted build. It ends with a verdict: **Up to date**, **Rolling upgrade**, **Needs a window** or **Blocked**. Right after an upgrade it shows **Waiting for migrate --post** until that step has run. The same check runs from a new release's image before you deploy it; see [Upgrades](/docs/self-hosting/upgrades#check).

### Background work

Background migrations, which rewrite existing rows in small batches while the instance serves, such as the usage history backfill and secret re-encryption after an upgrade to v0.11. Each shows its status and progress. Administrators can **Pause** and **Resume** one, and change its **Rows per batch** and **Pause between batches (ms)**; auditors see it read-only. Batches wait by themselves while a database standby lags or a long transaction is open. A migration that fails five times in a row stops as failed with the error shown; resume it once the cause is fixed. See [Upgrades](/docs/self-hosting/upgrades#background-migrations).

### Storage reconciliation

Compares file storage against the database in both directions. **Check for orphans** reports objects with no record and records with no object; **Queue orphans for deletion** hands the orphaned objects to the cleanup job. Worth running after restoring a backup. Records with no object are reported, not repaired. Objects newer than 24 hours, and backup and compliance objects, are never treated as orphans. **Storage in use** shows live bytes and files, what is in the trash, and how many objects are queued for removal.
