Released 2026-10-05. v0.11 is about keeping an instance running: upgrading from the previous minor release with no downtime, working through a PostgreSQL or Redis failover, and changing the embeddings model without a gap in search. Each of these is tested in CI, not only described. Upgrade with `migrate`, then replace replicas one at a time, then `migrate --post` ([below](#upgrading-from-v010)).

What the tests measured, on one machine running everything in Docker (not a production cluster):

| Test | Result |
|---|---|
| PostgreSQL failover drill: a three-node Patroni cluster under load, two failovers a minute apart | 1,173 requests, **0 failed**; 180 replies, all complete; a new primary promoted in about 2.5 s each time |
| Redis failover drill: the Redis primary killed twice under load, Sentinel promoting a replica | 1,439 requests, **0 failed**; 210 replies, all stored complete |
| Rolling upgrade from v0.10.2 under load: `migrate`, every replica replaced, `migrate --post`, background migrations | 2,392 requests outside the moments a v0.10.2 replica (which cannot drain) was stopping, **0 failed**; 223 replies, all complete; no lock waits |
| `helm upgrade` on kind under load (the chart's CI test) | 3,156 requests, **0 failed** |

And with the scale harness at 6,000 people and 4 million messages: the admin Usage spend tab went from 777 to 39 ms, the Usage overview from 606 to 94 ms, the admin overview from 126 to 22 ms (at 500,000 messages), and the passage search of a large project from 773 to 180 ms (p95, 1,000 people).

## For people

- **Long conversations load in parts.** A conversation opens at its latest 100 messages and loads earlier ones as you scroll up, without moving what you are reading. In a long conversation only the messages near the screen are drawn, so **your browser's Find (Ctrl+F or Cmd+F) only finds messages near the view**; use [conversation search](/docs/using/conversations#finding-a-conversation) to search all of it. See [Very long conversations](/docs/using/conversations#very-long-conversations).
- **Waiting for a busy model.** When your institution has set limits for a model and everyone is busy at once, your message waits its turn instead of failing: the reply shows "Waiting for *model* — you're number *N*", with **Stop**. See [Waiting for a busy model](/docs/using/limits#waiting-for-a-busy-model).
- **Web search is part of the reply's work block.** The search made before a reply is the block's first step, **Searched the web · 5 sources**, and links a connector returned are a **Sources** step, so a reply has at most one collapsed block above its answer. See [How a reply shows the model's work](/docs/using/chat#how-a-reply-shows-the-models-work).
- **Replies are not cut off when a server restarts.** A server that is stopped lets the replies it is writing finish; one that cannot finish in time is saved as interrupted, with **Retry**.
- **Read-only maintenance.** During a maintenance window you can still read, search, export and sign in; a banner says why changes are paused and until when. See [When OCI is read-only](/docs/using/chat#when-oci-is-read-only).
- **Signing out another device applies on its next request.** It used to take up to five minutes.

## For administrators

- **Read-only maintenance mode**, on **System health → Maintenance**: switch it on, or schedule a window with an announcement ahead of it. Reading, search, export and sign-in keep working; every change is refused, on every replica at once. See [Maintenance](/docs/administration/maintenance).
- **Provider capacity.** Limits per provider and per model (requests and tokens per minute, replies at once), shared across replicas. A message over a limit waits in a fair queue, with priority by role and a longest wait. A provider's `429` and `5xx` answers are retried before the reply's first output. See [Provider capacity](/docs/administration/providers-and-models#provider-capacity).
- **Changing the embeddings model leaves no gap.** The new model fills a new *generation* in the background while search keeps answering from the current one, then switches when it covers every passage. The tab shows progress and the cost before you save, with **Switch now** and **Cancel rebuild**. See [Changing the model](/docs/administration/embeddings-and-reranking#changing-the-model).
- **Usage pages, reports and budget checks read hourly totals**, exactly equal to the individual records, so they stay fast with years of history. See [How the figures are read](/docs/administration/audit-and-reports#how-the-figures-are-read).
- **System health** gains **Upgrades** (what an upgrade involves), **Background work** (background migrations, with pause and resume), a list of **Replicas**, and checks for **Background workers**, **Read-only mode**, **Cache invalidation**, **Encryption keys** and **Provider capacity**. See [System health](/docs/administration/instance-settings#system-health).
- **Sign-in limits count failures.** **Sign-in attempts per minute** now counts failed sign-ins per account; a client address has its own, much larger allowance (300 failures a minute by default), so a campus behind one address can sign in at once; single sign-on is limited per identity provider. See [Sign-in attempts](/docs/administration/budgets-and-limits#sign-in-attempts).
- **Settings changes reach every replica at once** (with Redis; within 30 seconds without it).
- **Role changes, bans and revoked sessions apply on the next request**, on every replica. They used to take up to five minutes.

## For operators

- **Three-phase migrations.** Pre-deploy migrations stay fast and transactional; post-deploy steps (`migrate --post`, after every replica runs the new release) build indexes concurrently; background migrations rewrite rows in throttled batches while OCI serves, with progress, pause and resume on System health. See [Upgrades](/docs/self-hosting/upgrades).
- **An upgrade preflight**, `node dist/scripts/upgrade-check.js` in the API image, lists each pending step with the tables it touches and their sizes, and answers *rolling*, *needs a window* or *blocked*. See [Check](/docs/self-hosting/upgrades#check).
- **Lock-safe migrations.** Each attempt has a 3-second lock timeout and is retried with backoff, so a migration waiting behind a long query no longer holds up every request behind it. `MIGRATION_LOCK_TIMEOUT_MS`, `MIGRATION_STATEMENT_TIMEOUT_MS`.
- **Draining on shutdown.** A stopping replica reports not ready, refuses new turns with `503` and `Retry-After` (the web app sends them again), lets replies finish for up to `SHUTDOWN_DRAIN_TIMEOUT_MS` (25 s) and saves anything left as interrupted. A reply whose replica died is recovered within about 20 s. See [Replacing replicas](/docs/self-hosting/upgrades#replacing-replicas-draining).
- **A worker role**: `OCI_ROLE=web|worker|all` (default `all`) runs background jobs on separate replicas; an optional `worker` Compose profile. See [Process roles](/docs/self-hosting/high-availability#process-roles).
- **Failover safety.** Reads caught by a dropped database connection are retried once; writes answer `500` with `retryable: true`; a new message and a reply's final save are retried; a job that loses its lock stops after its batch. See [What each layer survives](/docs/self-hosting/high-availability#what-each-layer-survives).
- **Connection pooling.** `DATABASE_URL` may now be PgBouncer in transaction mode; locks, `LISTEN`, post-deploy steps and backups use `CONTROL_DATABASE_URL`. `READ_DATABASE_URL` serves the admin overview and usage reports from a replica within 1 s of the primary.
- **Redis Sentinel and Cluster** (`REDIS_SENTINELS`, `REDIS_CLUSTER_NODES`), with bounded command timeouts and replies that survive a Redis failover. **Redis is required for more than one replica**; System health shows an error without it.
- **Encryption key rotation.** `ENCRYPTION_KEYS_PREVIOUS` decrypts alongside a new `ENCRYPTION_KEY`, background migrations re-encrypt every stored secret, and System health counts values still needing an old key. See [Rotating `ENCRYPTION_KEY`](/docs/self-hosting/security#rotating-encryption_key).
- **A Helm chart**, published to `oci://ghcr.io/ncecere/charts/open-chat-interface`, with migration hooks, draining, disruption budgets, a network policy and Pod Security `restricted`. See [Kubernetes with Helm](/docs/self-hosting/kubernetes) and [High-availability deployment](/docs/self-hosting/high-availability).
- **Images for `linux/arm64`** alongside `linux/amd64`, under the same tags.
- **Service objectives and alerts**: four published objectives, 47 Prometheus rules (recording, burn-rate and operational) and a Grafana dashboard in `deploy/monitoring`. See [Health and monitoring](/docs/self-hosting/health-and-monitoring#service-objectives-and-alerts).
- **Test tools in the repository**, all run in CI: a scale harness (`tools/scale`), a rolling-upgrade test under load (`tools/upgrade-test`), a failover drill (`tools/failover-drill`) and a migration linter (`pnpm lint:migrations`).
- **The web container drops every capability**: the caddy binary no longer carries a file capability. It still listens on 8080.
- **`503` from the API now means only "this replica is draining".** A failed stream resume answers `500`.

## Fixes

- A terminated database transaction during a failover no longer crashes the API or leaves its connection pool unusable (a patched database driver).
- Conversation search (`/api/threads/search`) was counted as `/api/threads/:id` in metrics.

## Upgrading from v0.10

From v0.10.x, with no downtime. Read the [v0.11.0 upgrade notes](/docs/self-hosting/upgrades#to-v0110) first. In short:

<Steps>
<Step>

### Back up and check

Back up the database. Run the preflight against it with the v0.11 API image (`node dist/scripts/upgrade-check.js`) to see the work and the verdict.

</Step>
<Step>

### Migrate

Run the v0.11 `migrate` job: migrations `0039` to `0041`, all fast. v0.10 replicas keep working on the new schema.

</Step>
<Step>

### Replace replicas

Replace API replicas one at a time, then the web containers.

</Step>
<Step>

### Post-deploy

Run `migrate --post`: post-deploy steps `0001` to `0006` build indexes concurrently, then schedule the usage rollup backfill and the re-encryption of stored secrets.

</Step>
</Steps>

<Callout type="warn" title="Rolling back after migrate --post needs the backup">
  After `migrate --post`, stored secrets are written in a new format that v0.10 cannot read. Rolling back to v0.10 from then on means restoring the pre-upgrade backup. Before `migrate --post`, v0.10 images still run on the new schema.
</Callout>

A single instance that migrates itself at startup (`RUN_MIGRATIONS=true`) runs the post-deploy step on its own. The Helm chart runs `migrate` and `migrate --post` as hooks around its rolling update.

Also:

- **`RATE_LIMIT_AUTH_PER_MINUTE` now counts failed sign-ins per account.** The address has its own limit, `RATE_LIMIT_AUTH_ADDRESS_PER_MINUTE` (300). Behind a proxy, `TRUSTED_PROXIES` still matters.
- **Do not change the embeddings model, or `ENCRYPTION_KEY`, during the upgrade.**
- With several replicas, configure Redis if you have not: System health now reports an error without it.

## Known limitations

- **Backups at scale** are not in this release: OCI's own backups are a `pg_dump`, which suits small and medium databases. Large clusters should use their own backups (pgBackRest, WAL-G).
- **One region.** Multi-region deployments are not designed for or tested.
- **The Helm chart bundles no PostgreSQL or Redis.** Use operators or managed services.
- **Your browser's Find** only finds the messages of a long conversation that are drawn.
- The latency objectives have been measured up to 6,000 people and 4 million messages, on a shared laptop, not yet at the harness's largest profile on dedicated hardware.
- There is still no multi-factor authentication for local accounts.
